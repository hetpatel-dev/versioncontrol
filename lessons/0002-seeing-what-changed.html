Lesson 0002

Seeing What Changed

~10 minutes · Mission: Career-ready Git
Goal: Learn to inspect changes before and after committing. These read-only commands are how you'll review work every single day on the job.

The problem

You just made 3 commits. But what actually changed in each one? On a real project, you'll need to check your changes before staging, review what's staged before committing, and look back at old commits to understand when a bug was introduced.

Step 1: Unstaged changes — git diff

Modify hands-on/hello.txt (add a line or change it), but don't stage it. Then run:

$ git diff

You'll see a line-by-line breakdown. Lines starting with + are additions (green). Lines with - are deletions (red). Git shows you the "before" and "after" side by side.

Readability trick git diff --word-diff highlights individual words that changed rather than whole lines. Great for prose or long variable names.

Step 2: Staged changes — git diff --staged

Now stage your change:

$ git add hands-on/hello.txt

git diff now shows nothing (there are no more unstaged changes). But the changes are staged. See them with:

$ git diff --staged

This is the "preview before you commit." Professionals always review their staged diff before committing.

Step 3: Look at a commit — git show

Commit and then inspect it:

$ git commit -m "Improve hello.txt greeting"
$ git show HEAD

git show HEAD shows the most recent commit: the metadata (author, date, message) plus the diff. You can show any commit by its hash:

$ git show cc7ddc1

(Use the actual hashes from your log.)

Step 4: Richer history — git log options

You already know git log --oneline. Now add more detail:

$ git log --oneline --stat

--stat shows which files changed in each commit and how many insertions/deletions.

$ git log --oneline --patch

--patch (or -p) shows the full diff for every commit — the complete story of your project.

$ git log --oneline --graph --all

--graph draws a visual tree of branches. --all shows every branch, not just the current one. Right now it'll just be a straight line — that changes once you start branching.

Career habit On a real team, you'll use git diff before every commit and git show to review others' commits during code review. These are daily tools, not advanced features.

Step 5: Bonus — undo safely

You already discovered git restore --staged. Here are two more safe undo commands:

# Discard unstaged changes to a file (permanent!)
$ git restore hands-on/hello.txt

# Fix the last commit message without changing its content
$ git commit --amend -m "Better commit message"
Caution git restore discards unsaved work permanently. Only use it on files you're sure about. git commit --amend is safe only for commits you haven't pushed yet.

Practice to build fluency

  1. Make 3 separate changes to hello.txt, committing each one
  2. After each, run git show HEAD to see what you just committed
  3. Run git log --oneline --stat --patch — scroll through your full history
  4. Use git diff before the next commit you make — build the habit

What you just learned

  • git diff — unstaged changes
  • git diff --staged — staged changes (pre-commit review)
  • git show <commit> — inspect any commit
  • git log --stat — files changed per commit
  • git log --patch — full diff per commit
  • git log --graph --all — visual branch tree
  • git restore — discard unstaged changes
  • git commit --amend — fix last commit
